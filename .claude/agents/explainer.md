## 1. Origin & purpose

**What it is.** Job Bunny is a personal, single-machine job-search pipeline. Several times a day it (a) scrapes saved LinkedIn job searches with Playwright over Chrome CDP, (b) pulls postings from keyless ATS APIs (Greenhouse, Keka), (c) structures/filters/ranks them against a resume profile, and (d) syncs survivors to a per-profile Notion database, with an optional Telegram digest. Cross-platform (macOS, Windows, Linux): scheduling is an in-process daemon (`jobbunny serve start|stop|status`, `src/ops/daemon/`; darwin-only autostart via `jobbunny autostart enable|disable`) — `launchd` triggering was retired 2026-07-27 — and Chrome discovery resolves per-OS candidate paths (`adapters/browser/cdp-chrome/discovery/`) rather than one hardcoded macOS path. Private, not on npm (`package.json` `"private": true`). `README.md:11-15`, `CLAUDE.md:7`.

**v0 vs v2.** v0 was plain JavaScript under `scripts/`, still on branch `main`. v2 is a **clean-room TypeScript rewrite** under `src/`, on `main-v2`. Rule: port implementation *know-how* (selectors, CDP handling, Notion schema quirks) by reading v0, never by copying its structure (`main-v2.md`, decision 2). `scripts/` is deleted on this branch — never reference it as a live path.

## 2. Architecture

### 2.1 The 10-stage pipeline

Frozen order, composed in `src/cli/wire/compose.ts`:

```
reconcile → farm → source → compress → structure → assemble → filter → dedup → rank → sync
```

Every stage is a `StageDef { name, timeoutMs, retries, heartbeat?, run(input, ctx) }` (`src/pipeline/runner/stage.ts`). The payload between stages is frozen: `StagePayload { jobs: JD[], dropped: DroppedRecord[] }`. `dropped` accumulates cumulatively so the funnel can attribute drops per stage.

| Stage | File | Role / inputs → outputs | Timeout/retries | Failure semantics |
|---|---|---|---|---|
| **reconcile** | `src/pipeline/stages/reconcile.ts` | Rebuilds the local mirror from the profile's PRIMARY CONNECTOR's store (the live Notion DB for `connector: notion`, the local sqlite file for `connector: sqlite`) via `Connector.rebuildCache`; writes `cache/entries.json` (`CACHE_PATH`). Payload passes through unchanged. **Read-only on that store.** | 60s / 0 | Fails loud — auth/network/malformed DB is a config problem, not a narrow casualty |
| **farm** | `src/pipeline/stages/farm.ts` | Runs each `FarmingLane` (LinkedIn) in order; collects jobs + card-gate drops; **side-writes `registry/companies_seen.json`**. `heartbeat: true`. | 90 min / 0 | One lane's total failure = warn, continue. **Every lane that ATTEMPTED work** failing = loud throw; a lane returning `skipped` (LinkedIn on a throttle cooldown) is excluded from that denominator and contributes no `companies_seen` entry. Run-level abort rethrown, nothing written |
| **source** | `src/pipeline/stages/source.ts` | Generic probe/fetch loop over every `ApiLane` (Greenhouse, Keka): reads `registry/companies.json` + `companies_seen.json`, `upsertSeen` → capped probes (`maxProbesPerRun` 25) → fetch boards → per-job **4-gate chain** (`stages/gates.ts`'s `runJobGates`, cheapest first: title/avoid card gate (`evaluateCard`) → seen-ledger skip (`registry/api_seen.json`) → Notion cache skip → `maxNewPerLane` cap (40)). Registry persisted once. | 300s / 0 | Whole-lane fail-soft; per-lane 90s budget (`laneBudgetMs`) whose expiry is a warn, never a run failure. Missing cache = warn + gate disabled (deliberate divergence from dedup) |
| **compress** | `src/pipeline/stages/compress.ts` | Truncates `rawText` to **2500 chars**, strips "about the job" boilerplate, escapes `\|`→`｜`; emits a 5-column input table (`id \| title \| company \| location \| rawText`, `location` from `identity.location`, empty cell when the lane gave none, capped 100 chars); writes `structure/table.json` and `structure/passthrough.json` (id→full JD) | — / 0 | Loud on a job missing `content.rawText`. Duplicate `identity.id` → first wins, later gets `compress.duplicate-id` DroppedRecord |
| **structure** | `src/pipeline/stages/structure.ts` | LLM normalisation via `ports/llm.ts`. 25-row batches, per-batch checkpoint to `structure/decisions.partial.json`, final `structure/decisions.json`. Output is a 10-column markdown decisions table (unchanged). Prompt prefers the input `location` column for city/country, inferring country from city when that's all it resolves, falling back to rawText only when `location` is empty. `heartbeat: true` but beats only *between* batches | 30 min | Missing ids warn; **wiring constraint**: guard `stallMs` MUST exceed the provider per-call timeout (300s) or the watchdog false-kills a healthy batch |
| **assemble** | `src/pipeline/stages/assemble.ts` | The **zod ingress boundary on untrusted LLM output**: joins decisions rows against the passthrough map by id, builds `structured`, validates against `StructuredSchema` | — / 0 | Per-row fail-soft: bad rows → `DroppedRecord{rule:'structure.unparseable', severity:'hard'}`. Loud only on missing input files |
| **filter** | `src/pipeline/stages/filter.ts` | `core/filter`'s `evaluate` + `decide` over `structured`. `drop` ⇒ DroppedRecord; `keep` ⇒ verdicts (soft *and* passing hard) appended to `evaluation.verdicts` so rank can penalize them | 30s / 0 | Loud if a job lacks `structured` |
| **dedup** | `src/pipeline/stages/dedup.ts` | Pure `core/dedup.dedupe(jobs, cache)` against the reconciled cache re-read from `CACHE_PATH` and re-validated | 30s / 0 | **Loud** if cache missing — silently treating it as empty would let everything sail past Notion |
| **rank** | `src/pipeline/stages/rank.ts` | Pure `core/rank.rank(jobs, cfg)` — 100-pt, 5 axes (`core/rank/axes.ts`), excitement banding, matchReasons, soft-verdict penalty | 30s / 0 | Loud if a job lacks `structured` |
| **sync** | `src/pipeline/stages/sync.ts` | `Connector.syncJobs` — writes automated fields only to the profile's PRIMARY CONNECTOR's store (Notion or the local sqlite file). Diffs input vs returned `SyncedJD[]`, emits a DroppedRecord per silently-dropped job. `opts.dryRunPath` writes the would-write set instead of calling the connector | 15 min / **0** | Per-page failures are `SoftError` inside the connector. `retries: 0` deliberate — `syncJobs` is not retry-idempotent, a stage retry could double-insert |

### 2.2 Layer model & boundary rules

`core/` (pure, no I/O) + `ports/` (TS interfaces) + `adapters/` + `pipeline/` + `routines/` + `ops/` + `cli/` + `app/` (2026-08-02: vertical feature slices over ports+core, adapters reachable only by injection — see below). Direction: `cli → pipeline/routines/ops → ports + core`, `adapters → ports + core`, and `cli → app → ports + core`.

Eight rules in `.dependency-cruiser.cjs`, run via `npm run boundaries`:

1. `core-is-pure` — `src/core` may not import `ports|adapters|pipeline|routines|ops|cli|app`
2. `ports-only-core` — `src/ports` may not import `adapters|pipeline|routines|ops|cli|app`
3. `adapters-no-cross-family` — an adapter family may not import another
4. `adapters-only-ports-core` — `src/adapters` may not import `pipeline|routines|ops|cli|app`
5. `only-wire-imports-adapters` — nothing except `src/cli/wire/compose.ts` (plus siblings `builders.ts` and `board.ts`, and a TYPE-ONLY exception for `registry.ts` — see §2.3) may import `src/adapters/**`
6. `nothing-imports-cli` — nothing imports `cli`
7. `app-only-ports-core` (2026-08-02) — `src/app` may not import `adapters|pipeline|routines|ops|cli`: the board layer reaches an adapter only via injection from `cli/wire`
8. `only-cli-imports-app` (2026-08-02) — nothing except `src/cli` may import `src/app`

**Parser gotcha:** parsing goes through `@swc/core` with `tsConfig` **omitted**. dependency-cruiser 18.x caps at typescript <7.0.0; setting `tsConfig` silently cruises 0 modules (a vacuous pass). swc tracks `import type` edges — which is what makes these rules fire, since most cross-boundary imports here are type-only.

`includeOnly: '^src'` means the `src/` → `scripts/` boundary, and everything under the separate `ui/` npm workspace, are **not** mechanically enforced by `boundaries` (nor by root `biome check src`/`filesize`, which likewise only target `src/`); `ui/`'s sole contact with `src/` is a type-only import of `src/app/features/*/index.ts` contract types via `ui/src/lib/api/types.ts` (erased at compile time by `verbatimModuleSyntax`, so no `src/` code is ever bundled into the frontend), gated instead by its own `ui:check`/`ui:build`.

Two documented exceptions inside `src/`: `cli/commands/stage.ts` imports `pipeline/runner/guard.ts` directly (single-stage runs get identical timeout/retry/stall semantics), and `test/invariants/run_cap_backstop.test.ts` lives outside `src/` so it can import both `cli/` and `adapters/`.

### 2.3 How `src/cli/wire/` works

`src/cli/wire/` (P8, split from a single 772-line `wire.ts` on 2026-07-28) is one module: `index.ts` is its public surface, and seven internal files do the work:

- `config.ts` — config loading (below), PURE.
- `registry.ts` — adapter-check assembly (below), mostly pure — **TYPE-ONLY exception**: `RuntimeDeps`'s `notionApi`/`browserReachable` fields are typed against two adapter-owned structural interfaces (`NotionApiLike` from `adapters/db/notion`, `CdpReachableFn` from `adapters/browser/cdp-chrome`) that predate this split, so `registry.ts` is exempted in `only-wire-imports-adapters` alongside `compose.ts`/`builders.ts` for those two type imports only — it constructs no adapter and does no IO itself.
- `settings.ts` — every settings default + resolver, PURE, no adapter imports (this is the file `only-wire-imports-adapters`'s negative-verification targets, precisely because it has no legitimate reason to need one). 2026-07-30: gained `resolveLoggingSettings(settings, envOverride?)` for `settings.logging` — parses `ops/observability`'s `LoggingSettingsSchema` (re-exported here, not redefined — `{fileLevel: 'debug', ttyLevel: 'info'}` defaults, missing/`{}` defaults quietly, present-but-invalid throws) and, when `envOverride` (the CLI's `JOBBUNNY_TTY_LOG_LEVEL`) is a valid `LogLevel`, replaces `ttyLevel` only.
- `builders.ts` — live connector/notifier/routine/lane construction (`buildConnector`, `buildNotifier`, `buildRoutine`, `buildLanes`, `buildLinkedInLane`), plus (2026-08-02) `missingTokenNotionClient` (moved here from `compose.ts`), the `wireMigrate`/`MigrateWire` composition seam for `jobbunny migrate` (a narrow Notion-read + lazily-opened sqlite-import handle, no full `wire()`), and the opt-in sqlite→Notion mirror decision (local-DB spec PR 3): private `mirrorSettings()` is the single authority — a structural `connector === 'sqlite' && notionSlice.mirror === true` short-circuit THEN `NotionConnectorSettingsSchema.safeParse`, so a malformed `settings.notion` slice always means 'no mirror', never a wire-time throw — with its two thin projections `mirrorDbId`/`buildMirroredConnector` and the doctor-facing `mirrorReachableCheck` (downgrades a mirrored profile's `notion-db-reachable` `red` to `warn`). Split out of `compose.ts` purely to keep it under the file-size cap.
- `compose.ts` — the **single composition point**, `realRegistry` + `wire()` itself.
- `testkit.ts` — shared fixtures for `config.test.ts`/`compose.test.ts` (a POSIX-literal fake repo root, a fake `readFile`, the profile/filter/data path helpers that key it). Test-only, not part of the public surface.
- `board.ts` (2026-08-02) — `wireBoard()` builds the cross-profile `BoardSource` the `board` command injects into `createBoardServer()`: tolerant per-profile discovery (`listProfiles()` — malformed/missing `profile.json` → `{name, connector: '', hasDb}`, never a throw) and `openStore(name)`, security-ordered — `name` must be a member of the CURRENT `listProfiles()` names, then `hasDb` must be true, only then a memoized `new SqliteBoardStore(openJobsDb(dbPath))` — membership, not path math, is the traversal defense against a raw `name` arriving from a URL param. Never creates a DB file. In the `only-wire-imports-adapters` carve-out alongside `compose.ts`/`builders.ts`.

Three independent things `wire()` ties together (2026-07-27: `wireScheduler()`, a fourth, was deleted alongside the `Scheduler` port — see §2.1/§6):

1. **Config loading** (`config.ts`) — `loadPipelineConfig`/`loadFilterConfig` read `profile.json`/`filter.json` via an injected `ConfigStore` (config→db Phase 4 — no `readFile`/`root` left; the store owns its own path resolution and legacy-file lift), then zod-validate (`PipelineConfigSchema`/`FilterConfigSchema`; `filter.json` missing ⇒ `undefined`, invalid ⇒ throw). Fail-loud, deliberately redundant with doctor's `profileParsesCheck` (reports `red` without throwing).
2. **Adapter-check assembly** (`registry.ts`) — `assembleAdapterChecks(config, registry, deps)` is **pure**: maps `lanes`/`connector`/`notifiers` names onto a `CheckFactory` registry. Unknown name ⇒ loud throw.
3. **Live composition** (`compose.ts` + `builders.ts`) — builds `Lane[]`, `Connector`, `Notifier[]`, `Routine[]`, `LlmProvider`, `BrowserProvider`; returns `{ ctx, stages, routines, checks }`.

Notable internals:
- **Two storage handles, deliberately** (rationale re-scoped in persist-to-db Phase 3): `storage` at repo root (machine-shared `src/adapters/lanes/linkedin/page_inventory/`, read by the LinkedIn lane's inventory checks), `profileStorage` at `profiles/<name>/data` — its only remaining production consumer is `routine cleanup`'s legacy `runs/<date>/` folder pruning (`listSubdirs`/`removeTree`); every other per-profile artifact that used to live on `profileStorage` (`cache/`, `registry/`, `structure/`, the LinkedIn lane's resume/capture state) moved onto `ctx.stateStore` (`ports/state_store.ts`, `SqliteStateStore`) in Phase 3 — see §4. A single repo-root handle (bug until 2026-07-25) made profiles share one cache/registry back when this port still carried that state.
- **Missing `NOTION_TOKEN` never crashes wiring** — a throwing-stub client (`missingTokenNotionClient`, `builders.ts`) backs the connector so the live path fails loud at first use, while `doctor` survives; `wireMigrate` shares the same stub and posture.
- `llm` and `browser` are **not** config-driven; settings sliced from `settings['claude-cli']` / `settings['cdp-chrome']`.
- Settings resolvers have two postures: *silently default* on bad/absent (`resolveInventoryMaxAgeDays` 30d, `resolveMaxCardsPerUrl` 40, `resolveMaxNewPerLane` 40) vs *fail loud* on nonsense (`resolveJitterRange`).
- `ctx.notify` uses `Promise.allSettled` — a notifier failure never flips a passed run to exit 1.
- `ctx.signal` / `ctx.beat` are placeholders; `runPipeline` and `guardStage` replace them.

### 2.4 The runner & watchdogs

`src/pipeline/runner/run.ts`'s `runPipeline` runs stages sequentially, checkpoints after each success, and **never throws** — failures become a `ctx.runStore.recordFailure` call (heartbeats too, via `ctx.runStore.heartbeat`) plus a `'failed'` `RunResult`; exit code is the caller's. Checkpoints (persist-to-db Phase 2) are rows in `jobbunny.db`'s `checkpoints` table, keyed `(run_date, time_dir, position)`, written via `ctx.checkpointStore` (`ports/checkpoint_store.ts`, `SqliteCheckpointStore` in `adapters/db/sqlite/checkpoints/`) — LOUD by contract (write failures throw and fail the run, unlike the run store's fail-soft posture). Each `run` invocation owns a FRESH `(date, timeDir)` group (local start time — `formatRunTime`/`ctx.checkpointStore.nextTimeDir`), never a shared per-day one; `runPipeline` itself is ignorant of group discovery — it only ever sees the group plus an optional `RunnerOptions.resumeFrom` seed (`{ startIndex, payload, checkpointPath? }`, the last field now a human-readable `"<date>/<timeDir>#<position>-<stage>"` descriptor, display/log-only). `cli/commands/run.ts`'s `--resume` handling does the discovery: before running, it finds the latest EARLIER same-day group via `ctx.checkpointStore.latestCheckpointTimeDir` (deliberately NOT `latestTimeDir`, which also matches a bare `runs` row with no checkpoint yet — the just-created fresh group is excluded automatically since it has no row yet either way), reads its latest checkpoint, and passes that as `resumeFrom`; absent that, the run starts from stage 0. The resumed run's own checkpoints land in its own new group. `stage <name>` (and `reconcile`) instead continue in TODAY's latest EXISTING group (creating one only when today has none), so a chain of ad-hoc single-stage runs shares checkpoints — this is `cli/commands/stage.ts`'s own logic, not `runPipeline`'s. `cli/commands/run.ts` opens the `runs` row via `ctx.runStore.startRun` before invoking `runPipeline` and closes it via `ctx.runStore.finishRun` once it returns; `RunResult` carries both `date` and `time` (the owning group's); `formatDigest` shows both in its banner.

#### 2.4a Run observability is DB-backed (runs-observability Phase 1)

The five per-run artifact files this KB used to describe (`run.log`, `heartbeat.json`, `result.json`, `failure.json`, `sync_dryrun.json`) are RETIRED — none of them are written anymore. Observability now lives in the profile's `jobbunny.db`, `runs`+`run_events` tables, behind the `RunStore` port (`src/ports/run_store.ts`) and its sqlite implementation (`SqliteRunStore`, `src/adapters/db/sqlite/runs/store.ts`, schema `LATEST_SCHEMA_VERSION = 2` — `store/migrations.ts` is still the only place the schema is defined/evolved). `PipelineCtx.runStore` (`src/pipeline/runner/context.ts`) is present on every wired profile regardless of connector — a lazy-open `SqliteRunStore` over `profiles/<name>/data/jobbunny.db`, so `wire()` itself never touches the filesystem for it. Every `RunStoreWriter` method is fail-soft by contract: an open failure or SQL error warns once on stderr and degrades the store PERMANENTLY to a no-op (`startRun` returns `-1`, readers return empty) rather than ever failing a run — this holds for notion-connector profiles too, since every profile gets a `jobbunny.db` now. `'crashed'` status is DERIVED on read, never reconciled into the row: a `'running'` row whose `heartbeat_at` is null or older than `RUN_HEARTBEAT_STALE_MS` (10 minutes) displays as `'crashed'` in `listRuns`/`getRun` (`deriveStatus`, shared by `SqliteRunStore` and the board's read-only `SqliteBoardStore`); `startRun` additionally tidies PRIOR stale `'running'` rows to `'crashed'` for real before inserting the new row. Checkpoints moved off disk into this same `jobbunny.db` in persist-to-db Phase 2 (`checkpoints` table, `ports/checkpoint_store.ts` — see §2.4 above); no run creates any file under `profiles/<name>/data/runs/` anymore. Read paths: `jobbunny runs --profile <name> [show <id>]` (`src/cli/commands/runs.ts`, reusing the board's own `wireBoard` composition point — no new adapter) and the board API's `GET /api/profiles/:name/runs[/:id[/events]]` (`src/app/features/runs/routes.ts`).

Three watchdog layers:
1. **per-stage timeout** — `guardStage` composes `AbortSignal.any([ctx.signal, AbortSignal.timeout(stage.timeoutMs)])`; each retry gets a fresh budget
2. **heartbeat stall** — only for `heartbeat: true` stages; `childCtx.beat()` re-arms a `stallMs` timer; silence aborts the attempt's own `AbortSignal` (folded into `attemptSignal` via `AbortSignal.any`, so the in-flight work is actually cancelled rather than a separate bespoke stall promise rejecting while the real work kept running uncancelled). `DEFAULT_STALL_MS = 360_000` — above structure's 300s provider timeout by design
3. **global run cap** — `runCapMs`, derived by `computeRunCapMs` in `src/cli/commands/run.ts` as `Σ(timeoutMs × (retries+1)) × 1.25` (derivation closed P9 incident #2: a hardcoded 30-min cap under a ~68-min stage sum)

## 4. Data flow & state

**`profiles/<name>/`** (gitignored except rajni fixture):
- `profile.json` — lanes, connector, notifiers, routines, schedule, settings. **Notion DB/page IDs live here, never `.env`.**
- `filter.json` — the sole geo/skills/rank-gate authority; `locations[]` the only geo source.
- `resume.json` — hand-maintained; `search_urls.md` — Channel → `### <page-slug>` → `• <label> - <url>`, drives `lane add-url`/`/page-analyse`.
- `avoid.md` — read by no runtime code; edit `filter.json` instead. Never seeded (config→db Phase 4 dropped `profile build`'s `avoid.md` seeding — dead surface; existing files untouched).
- As of config→db Phase 4, these four docs are file paths in NAME only — the runtime source of truth is `data/jobbunny.db`'s `config_docs` table; the legacy files above are lift sources (and `config export`/`import` round-trip targets), not what any reader parses once a row exists. See the Config paragraph below for the mechanism.
- `data/` — `jobbunny.db` (every profile, regardless of connector — see §4's runs-observability note below; also holds the `checkpoints`, `state_docs`, and (config→db Phase 4) `config_docs` tables now). `cache/entries.json`, `registry/{companies,companies_seen,api_seen}.json`, `structure/*`, `lanes/linkedin/*` are LEGACY relPaths only as of Phase 3: every read/write of them moved onto `ctx.stateStore`'s `state_docs` rows (see the State paragraph below); a pre-Phase-3 profile's existing files are lifted into the DB once, lazily, on first read, and never written again. No `runs/<date>/` folder tree — retired in persist-to-db Phase 2; a run creates **no files** under `profiles/<name>/data/runs/` anymore (legacy pre-Phase-2 folders, if present, are still pruned by `routine cleanup`).

**Checkpoints (persist-to-db Phase 2)** — no longer files; rows in `jobbunny.db`'s `checkpoints` table, PK `(run_date, time_dir, position)`, plus `stage`, `payload_json`, `written_by` (provenance: the writing invocation's own `runs` row id, `NULL` if absent), `created_at`. One `(run_date, time_dir)` group per run invocation (local start time), not per day — matches the pre-Phase-2 folder's own grouping, just as DB rows instead of a directory. Writes are `INSERT OR REPLACE` (slot-overwrite on a same-stage rerun, matching the file era's same-filename overwrite) via `ports/checkpoint_store.ts`'s `CheckpointStore.write`, LOUD — a write failure throws and fails the run (deliberate contrast with the run store's permanent fail-soft degradation: checkpoints are recovery data, so silently losing one turns a resumable failure into a from-scratch rerun). The five artifact files this KB used to describe here — `run.log`, `heartbeat.json`, `result.json`, `failure.json`, `sync_dryrun.json` — are RETIRED (runs-observability Phase 1); none are written anymore. That same information (log events with a `scope` field from the runner/`stage` command's `withScope` wrapping, heartbeats, outcome+timings+funnel, failure detail, sync dry-run reports) now lives in `profiles/<name>/data/jobbunny.db`'s `runs`+`run_events` tables via `ports/run_store.ts` (`ctx.runStore`, present on every wired profile) — see §2.4a. Read paths: `jobbunny runs --profile <name> [show <id>]` and the board API's `GET /api/profiles/:name/runs[/:id[/events]]`. `routine cleanup` prunes `checkpoints` rows by `run_date` past `settings.cleanup.runsOlderThanDays` (default 30, never today) via `ctx.checkpointStore.pruneOlderThan`, AND separately prunes `runs` rows older than the same TTL via `ctx.runStore.pruneRunsOlderThan`, plus (legacy, pre-Phase-2 leftovers only) any lingering `runs/<date>/` folders on disk.

**State (persist-to-db Phase 3)** — the ten per-profile JSON state files (`cache/entries.json`, `registry/{companies,companies_seen,api_seen}.json`, `structure/{table,decisions,decisions.partial}.json`, `lanes/linkedin/{captures,extract_resume}.json`) are no longer files either; they are rows in the SAME `jobbunny.db`'s `state_docs` table (`key TEXT PRIMARY KEY`, `value_json TEXT NOT NULL`, `updated_at TEXT NOT NULL`; schema `LATEST_SCHEMA_VERSION` is now 4), keyed by their legacy relPath strings verbatim — zero constant churn, since those strings were already exported constants (`CACHE_PATH`, `RESUME_STATE_PATH`, etc.) owned by the modules that read/write them. `ports/state_store.ts`'s `StateStore` (`readDoc<T>(key, schema)`/`writeDoc(key, value)`/`close()`) is LOUD like `CheckpointStore`, unlike `RunStore`'s permanent fail-soft degradation: a lost registry write would silently reintroduce already-seen jobs as new, so any sqlite error propagates straight out. The one-time mechanism that lets an upgrading profile's existing files survive the cutover (ledger L9): `SqliteStateStore.readDoc` (`adapters/db/sqlite/state/`), on a DB miss, lazily lifts the legacy file at `<dataDir>/<key>` — parses it, validates it against the CALLER's schema before writing (so a legacy file that no longer matches the current schema stays a transient, fixable read error instead of being cemented into `state_docs`), `INSERT OR REPLACE`s it into `state_docs`, and returns the value. The legacy file itself is never deleted or modified; nothing writes it again, so once its row exists the file goes permanently inert. `PipelineCtx.stateStore` replaces `ctx.storage`/`ctx.profileStorage` for every stage that used to call `readJson`/`writeJson` on those ten keys (reconcile, source, compress, structure, assemble, dedup, farm, plus `cli/commands/reconcile.ts`); the LinkedIn lane's `capture_store.ts`/`resume_state.ts` and `lane.ts`'s cache read receive the same port via injection through `cli/wire/compose.ts` — inventory reads keep the `Storage` port. The `/structure` skill can't reach `ctx.stateStore` directly (it's Claude Code shelling out inline, not the pipeline's own Node process), so two narrow CLI helpers stand in (`src/cli/commands/state.ts`, restricted to exactly the three structure hand-off keys, not a general DB poke tool): `jobbunny state read <table|decisions|decisions-partial> --profile <p>` prints the raw doc to stdout, and `jobbunny state write <decisions|decisions-partial> --profile <p>` reads the doc from stdin (refuses a TTY — must be piped). `.claude/commands/structure.md` is wired to these helpers.

**Config (config→db Phase 4)** — the four per-profile hand-edited documents (`profile.json`, `filter.json`, `resume.json`, `search_urls.md`) are no longer files either; they are rows in the SAME `jobbunny.db`'s `config_docs` table (`key TEXT PRIMARY KEY` — the legacy filename verbatim, `value_text TEXT NOT NULL` — RAW document text, never a parsed-then-reserialized value, `updated_at TEXT NOT NULL`; schema `LATEST_SCHEMA_VERSION` is now 5), behind `ports/config_store.ts`'s `ConfigStore` (`readText`/`writeText`/`close`). Same one-time lazy-lift precedent as Phase 3's `state_docs` (ledger L9): `SqliteConfigStore.readText` (`adapters/db/sqlite/config/`), on a DB miss, reads the legacy file at `<profileDir>/<key>`, validates it (JSON-validity only for the lift — deliberately NOT the full schema, so a legacy file with rajni's tolerated v0-shaped keys still lifts), `INSERT`s the raw text unmodified, and returns it; the legacy file itself is never modified/deleted, and once its row exists the file goes permanently inert — a later hand-edit to it is silently ignored by every reader from then on. `ops/doctor/aggregate.ts`'s `configLegacyDivergenceCheck` (`config-legacy-divergence`) is the one signal that this happened: it compares each doc's CURRENT on-disk legacy text against what the store actually returns and `warn`s (never `red`s) naming the re-sync path (`jobbunny config import`) on drift; a doc with no legacy file, or one whose read fails, is silently skipped. `writeText` validates FIRST via `core/config/validators.ts`'s `validateConfigDoc` (zod at the write boundary: full schema for `profile.json`/`filter.json`, JSON-validity only for `resume.json` — its own zod schema is dead code that doesn't match reality — non-empty for `search_urls.md`) and never touches the legacy file. The db path is now canonical and fixed (`profiles/<name>/data/jobbunny.db`, `canonicalDbPath` in `cli/wire/builders.ts`) — `settings.sqlite.path` is RETIRED: a config still setting it is a LOUD wire error (`assertSqlitePathRetired`) and a doctor `red` (`sqlite-path-retired`), collapsing the hand-rolled `settings.sqlite` path walks `board.ts`/`daemon.ts` used to do. `wire()`, `board.ts`'s `readProfileInfo`, and `daemon.ts`'s schedule-config read (`ops/daemon/scan/scan.ts`'s injected `readProfileJson`) all construct a short-lived `ConfigStore` (`wireConfigStore`, `cli/wire/builders.ts`) rather than reading a file directly now — `liftMode: 'readonly'` for doctor/board/daemon (never creates or migrates `jobbunny.db` as a side effect of a read), `'readwrite'` (the default) for setup/`jobbunny config`/writers. Write surfaces: `jobbunny config get|set <doc> --profile <p>` (raw text over stdout/stdin, TTY-refused) and `config export|import --profile <p> [--dir <d>]` (round-trip to/from the four legacy-named files, byte-exact); `lane add-url`'s string surgery and `profile build`'s seed-never-clobber templating both now write through the same store, and `jobbunny migrate --apply`'s `profile.json` read-modify-write does too. The board's write surface (the CLAUDE.md hard rule, ledger L7) is now `tracking` PLUS this table: `GET`/`PUT /api/profiles/:name/config/:doc` (PUT 422s with the zod message on a validation failure) and `POST /api/profiles` (name-sanitized `^[a-z0-9_-]+$`, seeds a fresh profile's docs via the same `seedProfileDocs`/`profile build` path) — `jobs` and the `runs`/`run_events`/`checkpoints` tables stay pipeline/runner-only. `src/core/profile/` (the old `ResumeSchema`, zero importers) was deleted alongside this phase.

**The profile's PRIMARY CONNECTOR's store is the source of truth** — Notion for `connector: notion` profiles, the local sqlite file for `connector: sqlite` profiles. `reconcile` rebuilds the cache from that store every run (`Connector.rebuildCache`); local cache always rebuildable, never authoritative; `sync` writes only automated fields to that store. `jobbunny migrate` (2026-08-02) is the one-way bridge between the two: a one-shot Notion → sqlite import, never the reverse. A sqlite profile may additionally opt into `settings.notion.mirror: true` (2026-08-02, local-DB spec PR 3, `adapters/db/mirror`): `sync` best-effort pushes the same synced jobs to Notion too, but Notion is never read back — `reconcile`/`rebuildCache` and `archiveStale` never consult the mirror — so mirror failure or slowness can never affect the sqlite source of truth.

**Secrets.** `NOTION_TOKEN`, `TELEGRAM_BOT_TOKEN` live in `.env` under the data home, loaded once via an explicit `dotenv.config({ path: join(resolveHome(), '.env') })` inside `src/cli/main.ts`'s `isMain()` bin guard (`dotenv` is a de-facto 4th runtime dep). The board server (2026-08-07) writes secrets via a guarded `PUT /api/secrets/:key` (`features/secrets/routes.ts`): allowlist check before the body is even parsed, then quotes/backticks/backslashes are rejected, not escaped (`.env`'s format has no escaping convention for them); `GET /api/secrets` is presence-only, never values. A board-written secret does NOT take effect in that already-running board process — `dotenv.config()` ran once at startup, so its env stays stale until restart.

**`src/adapters/lanes/linkedin/page_inventory/<page>.json`** — machine-shared, colocated inside the owning adapter (`page_inventory/` is LinkedIn-lane config, not repo-root-shared machinery) and read at runtime by `adapters/lanes/linkedin/inventory.ts`. Every selector except `pagination` required non-empty — the zod schema is the completeness gate. `behaviors` carries `paginationType/Param/PageSize`, `maxPages`, `jdSettledSignal`, `jdAnchorText`, `maxRawTextChars`, `jobCardIdAttr`, `scrollContainer`, `mustExist`, `minJobCards`. ## 5. Conventions & invariants

- **Two-pair rule** — every module is a folder with an `index.ts` public surface; internals never imported across boundaries. A folder exceeding **two implementation files** (test pairs and `index.ts` excluded) splits into subfolders before the third lands.
- **Colocated tests** — `foo.ts` + `foo.test.ts`; `node:test` only. Test command uses glob form (`node --test "src/**/*.test.ts"`) — bare-directory args throw MODULE_NOT_FOUND on Node 24.
- **Fail-soft vs fail-loud** — `SoftError` = one URL/company/board/page: recorded, continue. Everything else fails the stage loudly. A stage that attempted work and captured nothing throws loud.
- **Verdicts, not silent drops** — every gate emits `DroppedRecord { jd, reasons: Verdict[] }`.
- **AbortSignal everywhere** — `AbortSignal.timeout()`/`.any()`; no unbounded await in any adapter; every CDP/network/LLM call bound by `ctx.signal`.
- **Token efficiency on the structure path** — JD text capped 2500 chars; structure input AND output stay markdown tables, not JSON.
- **Notion select options byte-exact** (`adapters/db/notion/schema.ts`, pinned by test). Inserts and anchored updates only; never whole-page overwrite/hard delete; cleanup archives (30-day undo), gated by `settings.notion.dryRun` (default `true`).
- **Mirror is best-effort, create-only, and never read back** (2026-08-02, `adapters/db/mirror`). It never fails or stalls a run, but its correctness rests on `dedup` dropping already-known ids before `sync` — every job reaching the mirror is new, so the push reuses `NotionConnector.syncJobs`'s insert path verbatim. A job archived locally and later re-scraped passes `dedup` again (archived rows drop out of the cache) and creates a SECOND Notion page while the original stays live — an accepted v1 hazard, since the mirror never archives Notion.
- **Config is the wiring** — pipeline never names a concrete adapter; only `cli/wire/compose.ts` instantiates.
- **Lanes are config-driven** — DOM drift fixed by regenerating `src/adapters/lanes/linkedin/page_inventory/*.json` via `/page-analyse`, never lane-code edits.
- **Farm writes what source reads** (`registry/companies_seen.json`).
- **Runner is the single notifier** — both digests built from the run's `RunResult`, now sourced from the `runs` table's `result` blob rather than a `result.json` file (§2.4a).
- **Seeding never clobbers** — `profile build` fills gaps; reruns propose a diff.
- **`profile remove`** dry-run by default, refuses `rajni`; `--force` deletes; never touches Notion.
- **No PDF parsing in the daily path.**
- **Stack** — ESM, TS7 (`strict`, `noUncheckedIndexedAccess`, `erasableSyntaxOnly` — no enums/namespaces, `verbatimModuleSyntax`, `allowImportingTsExtensions`, `noEmit`), zod, Biome (2-space, 90 cols, single quotes). Node ≥24, native type-stripping, zero build step.
- **3-runtime-dep cap** — `@notionhq/client`, `playwright`, `zod` (+ de-facto `dotenv`).
- **Docs are code** — per-module contracts, this KB, and the executor agent's rules updated in the same change that alters behavior.
- **The gate**: `npm run check` = typecheck && lint && boundaries && test. CI's `test` check now ALSO requires the separate `ui` job (`ui:check` = tsc (app + e2e configs) + biome + vitest, then `ui:build` = vite build, then a Playwright e2e run) to pass — the `ui/` workspace (`workspaces: ["ui"]` in root `package.json`) is not part of `npm run check` itself. `main` protected — land via PR.
- **Node 24 is the machine default** (since 2026-07-26; `nvm alias default 24`) and `.nvmrc` pins the repo, so plain commands just work; fall back to `source ~/.nvm/nvm.sh && nvm use 24 && <command>` only if `node -v` ever regresses below 24.

## 6. Ops

**CLI surface** (`src/cli/main.ts` USAGE): run / doctor / reconcile / stage / routine / serve start|stop|status (cross-profile) / autostart enable|disable (cross-profile, darwin only) / lane add-url / profile build|remove (2026-08-02: `build` now scaffolds `connector: 'sqlite'` by default, local-DB spec §8 — `'notion'` remains a valid opt-in) / setup (idempotent step checklist: profile scaffold, `.env NOTION_TOKEN` — skipped unless `connector: notion` or the sqlite→Notion mirror is active, mirroring `mirrorSettings()` in `cli/wire/builders.ts` — resume.json, search_urls.md, page_inventory coverage checked against the config docs (the runtime authority), and `ui build` checking `ui/dist/index.html`) / release / migrate [--apply] (2026-08-02: one-shot Notion → local sqlite import, dry-run by default; `--apply` imports insert-only then flips `profile.json`'s `connector` to `sqlite`) / board [--port <n>] (2026-08-02: profile-less local job-board HTTP server, binds `127.0.0.1` only, default port 1994, foreground until SIGINT/SIGTERM) / runs [show <id>] / state read|write / config get|set|export|import (config→db Phase 4: raw-text CRUD + file round-trip over the four config docs — see §4's Config paragraph). `--profile` required except `serve`, `autostart`, `release`, and `board`.

**Data home.** All user data (`profiles/<name>/` incl. each per-profile sqlite db, `.env`, the daemon pidfile, the persistent Chrome profile `chrome/`) lives under `~/.jobbunny/` by default. `src/cli/home/` (`resolveHome(env, homedir)`) is the single resolver: `JOBBUNNY_HOME` from the real shell env (never `.env` — circular, since `.env`'s own location is derived from the resolved home) overrides `join(homedir(), '.jobbunny')`; every `overrides.root` default resolves through it. A repo checkout is itself a valid home (`JOBBUNNY_HOME=$PWD`, the `verify` skill's convention — keeps the committed `profiles/rajni/` fixture reachable). Deliberate exception: `release` stays `process.cwd()`-based (a maintainer command operating on the git checkout, not user data). Program files (LinkedIn `page_inventory/*.json`, `ui/dist`) resolve from the package root via `import.meta.url`, never from the data home — the package-root/data-home split is intentional so a packed npm install and a dev checkout share the same home-resolution logic. `main()`'s dispatch order: `--help`/`-h` first (works with no home at all) → node-version guard (`nodeGuardMessage`) → daemon-liveness warning → arg parse → `defaultCheckHome` (skipped for `HOME_EXEMPT_COMMANDS = {setup, migrate-home, release}`; else `existsSync(resolveHome())` false ⇒ prints `` no jobbunny home at <path> — run 'jobbunny setup' `` and returns exit 1) → dispatch. `jobbunny migrate-home [--from <path>] [--apply]` is a one-shot bridge for legacy repo-local installs into `~/.jobbunny` (dry-run by default, refuses while the daemon runs, never clobbers an existing home, leaves the committed `rajni` fixture in the repo) — slated for removal once the fleet has migrated.

**`run` order**: acquire cross-process lock (skip, don't queue) → doctor preflight → pre-run routines → `runPipeline` → post-sync routines only if passed → digest exactly once → release lock. A crash before a `RunResult` exists exits 1 without notifying.

**Scheduling (in-process daemon, 2026-07-27).** Times/weekdays/grace live in `profile.json`'s `schedule` block (`times[]`, `enabled`, `weekdays[]` default Mon–Fri, `graceMinutes` default 90). `jobbunny serve start` splits into a parent (pidfile acquire under its OWN pid as a `wx` boot-window placeholder, darwin legacy-plist migration refusal, detached spawn, 2s alive-confirm via the spawn handle — the parent never rewrites `pid`) and `--daemon-child` (claims `pid` for itself as its first action, then the tick loop; on SIGTERM it stops the daemon and `process.exit(0)`s rather than unwinding, since an in-flight run child's handle would otherwise hold the event loop open for that child's whole runtime). Every 30s the daemon asks the pure `core/schedule/owed.ts`'s `isRunOwed(now, schedules, history)` which `(profile, slot)` pairs are owed — `history` merges each profile's own `runs` TABLE (read via `RunStoreReader.listRunTimeDirs`, a fresh short-lived `SqliteRunStore` per read wired by `cli/wire/daemon.ts`'s `wireDaemonRunHistory`; a profile whose db file doesn't exist yet contributes no records WITHOUT creating one) with the pidfile's own `attempts` ledger, so a slot that crashed before its first checkpoint doesn't respawn every tick for the rest of its grace window. (Folder scanning — the old `scanRunHistory` over `runs/<date>/` directory names — is retired: those folders stopped being written once checkpoints moved into `jobbunny.db`, persist-to-db Phase 2.) Owed slots run strictly sequentially, in `(slot, profileName)` order (one shared Chrome/CDP session), each firing `jobbunny run --profile <p> --headless` supervised by `ops/daemon/supervise/` (rotate `runs.log`, spawn, track `inFlight`, SIGTERM→20s→SIGKILL backstop at `runCapMs+300s` — a faithful port of the retired plist's embedded bash watchdog). `jobbunny serve stop` kills the daemon BEFORE any `inFlight` child (killing the child first could let the daemon spawn the next owed run before its own SIGTERM lands). `jobbunny serve status` reports liveness/uptime/wedged-heartbeat/next-fire, read-only. Darwin-only autostart: `jobbunny autostart enable` writes one `RunAtLoad`-only LaunchAgent (`com.jobbunny.autostart.plist`, no `StartCalendarInterval` — zero schedule knowledge) invoking `jobbunny serve start` at login, carrying `WorkingDirectory` (repo root), `EnvironmentVariables.PATH` (the enabling shell's PATH, captured at `enable` time — launchd's bare `/usr/bin:/bin:/usr/sbin:/sbin` has no `claude`, so every scheduled run died on the child's preflight), and `StandardOutPath`/`StandardErrorPath` → `daemon.log` (the parent's own refusals would otherwise go nowhere); Windows/Linux autostart remain a documented manual step (README). Logs → `~/.jobbunny/logs/{daemon,runs}.log` (replaces the macOS-only `~/Library/Logs/JobBunny/`; 2026-07-30: each daemon line is now structured NDJSON — `{ts, level, msg, data}` via `createDaemonLogger`, mechanism/rotation unchanged — with `spawn-error`/`tick-failed` at `error` and `backstop-expired`/`ledger-append-failed-skipping`/`heartbeat-write-failed` at `warn`).

**Release flow.** `npm run release -- <X.Y.Z> [--dry-run] [--no-merge] [--yes]` — the `--` is mandatory. Idempotent/resumable; pauses for explicit go-ahead before squash-merge unless `--yes`; does NOT write the CHANGELOG (that's `/wrap ship`). Never background/detach — merge prompt needs stdin.

**Doctor.** Core checks + adapter-contributed: LinkedIn → inventory freshness (30d default) + CDP reachable; Notion → DB reachable; sqlite → `sqlite-db-openable` (read-only open; a missing db file is `ok`, not a warning — it's created on first run); Telegram → `getMe`. 2026-08-01: `env-tokens` is connector-aware — a missing `NOTION_TOKEN` is `red` only when `profile.json`'s `connector` is `notion`, else `warn` (a sqlite-connector profile needs no Notion token at all); 2026-08-02: a mirrored sqlite profile (`settings.notion.mirror: true`) gets a mirror-specific warn detail instead of the generic one, and — when a live `notionApi` dep exists — an extra `notion-db-reachable` check via `mirrorReachableCheck` (`cli/wire/builders.ts`), which downgrades that check's `red` to `warn` (suffixed `— mirror only; local runs are unaffected`) since a broken mirror never impairs the sqlite profile's actual source of truth. config→db Phase 4 adds two core checks (`ops/doctor/aggregate.ts`/`config_checks.ts`) to the fixed eight-check `coreChecks()` order: `sqlite-path-retired` (`red` iff `profile.json`'s `settings.sqlite.path` is still set) and `config-legacy-divergence` (`warn`, never `red` — see §4's Config paragraph). `wire()` is called with `{ configLiftMode: 'readonly' }` for `doctor` specifically, so running doctor never creates or migrates a profile's `jobbunny.db` as a side effect. Exit 1 iff any `red`; `warn` never fails.

**Slash commands — only four**: `/setup` (Notion adopt-or-create, secrets, resume parse), `/page-analyse <page-slug>` (browser DOM analysis → `src/adapters/lanes/linkedin/page_inventory/<page>.json`; refresh values in place, bump `generatedAt`), `/structure` (LLM stage inline, byte-identical file contracts), `/wrap` (close-out; `jobbunny release` for ship).
