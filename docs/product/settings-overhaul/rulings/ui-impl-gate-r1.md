**FINDINGS**

**1. CRITICAL — `ui/src/features/settings/sections/ScheduleSection.tsx:91` — a fourth unguarded in-section nav trigger, newly load-bearing because of this very commit.**
`DaemonBridgeLine` renders "Manage the daemon on Operate →" with `onClick={() => navigate({ name: 'setup' })}`, using the raw app-wide `navigate` imported at line 14 — not `useGuardedNavigate()`. The component is rendered unconditionally inside the section body at `ScheduleSection.tsx:250`. Before 386732b this was inert-but-harmless (Schedule never registered, so no guard applied anywhere); 386732b added `useRegisterSettingsSave` at `ScheduleSection.tsx:220`, making Schedule dirty-aware for the settings nav and sidebar while leaving its own internal link unguarded. Net effect today: edit run times / weekdays / grace minutes, click "Manage the daemon on Operate →", and the draft is silently discarded with no dialog — the exact defect class R5 exists to prevent. My exhaustive sweep of `ui/src/features/settings/` (`grep -rnE "navigate\(|<a[[:space:]]+href|location\.(hash|href)[[:space:]]*="`, non-test) returns exactly five in-section triggers: this one, plus `LandingRulesSummary.tsx:68`, `LandingCapsTable.tsx:150`, `LandingSection.tsx:92` and `DangerZone.tsx:62` — all four of those live in the only two sections that legitimately do not register (Landing is read-only; DangerZone's `navigate` at :62 fires only *after* a successful profile deletion, and its `confirmText` is a confirmation field, not a draft). So this is the sole remaining hole.
**Condition to clear:** replace the raw `navigate` at `ScheduleSection.tsx:91` with `useGuardedNavigate()` (identical to the three fixes already applied at `RawConfigSection.tsx:220`, `RolesCompaniesSection.tsx:249`, `WhereYouWorkPrefsCard.tsx:103`), and add a `ScheduleSection.test.tsx` case that renders the section inside a real `SettingsSaveProvider`, dirties the schedule, clicks the button, and asserts `dirty-nav-dialog` appears *and* `navigate` was not called.

The only two tests covering the migrated triggers — `RolesCompaniesSection.test.tsx:232` and `WhereYouWorkPrefsCard.test.tsx:51` — both render standalone, *outside* a `SettingsSaveProvider`; the latter says so in its own comment ("Outside a `SettingsSaveProvider` … `guardedNavigate` falls back to the plain unguarded `navigate`"). Grep for `Unsaved changes|dirty-nav|Save and continue` across `ui/e2e` returns zero hits. The suite is green (1000/1000) on a check that could not have failed for this property. **On the two judgment calls, explicitly:**
- **(i) minimal registration for Schedule/AboutYou — acceptable.** `isDirty` tracks every *persisted* field each section writes: Schedule's snapshot (`times`, `enabled`, `weekdays`, `graceMinutes`) is exactly the set `handleSave` writes into `cfg.schedule` at `ScheduleSection.tsx:192-195`; AboutYou's `ResumeForm` is exactly the seven keys `applyForm` writes at `AboutYouSection.tsx:56-65`. Only the uncommitted-draft gap in finding 5 remains, which is out of scope for the persisted contract.
- **(ii) the third `DirtyNavGuard` instance — acceptable, structurally.** All three instances are driven by the same `isDirty` and the same context-delegated `save`/`discard` (`SettingsSaveContext.tsx:98-99`, read from `currentRef` at call time, so never a stale closure), so no instance can fire the wrong section's save. My only reservation is that none of this is pinned by a test (finding 2).
