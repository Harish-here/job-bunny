## Recon digest C — the observability CEILING (most load-bearing recon)

`runs` table (src/adapters/db/sqlite/store/migrations.ts:56-69): date, timeDir, kind
('run'|'stage'|'reconcile'), status ('running'|'passed'|'failed'|'crashed'), startedAt,
finishedAt, resumed_from (FK, nullable), result_json, failure_json, sync_dryrun_json, heartbeat_at.

`run_events` (migrations.ts:71-79): ts (ISO), level (debug|info|warn|error), msg, data_json.

WHAT EXISTS:
- Per-stage metrics (name, elapsedMs, attempts, jobsIn, jobsOut, dropsByRule) exist ONLY as JSON
  inside `result_json` (RunResult schema: src/ops/observability/run/result.ts:10-19, written at
  run.ts:302). No per-stage table → not SQL-queryable, only parseable.
- Failure capture (RunFailure, src/ports/run_store.ts:36-41, written run.ts:99-106): stage name,
  error message, elapsedMs, lastCheckpoint descriptor.
- Soft errors ARE persisted — as warn-level `run_events` rows with structured `data_json`
  (lane, company, error) e.g. source.ts:225-229, guard.ts:44-49. No aggregation anywhere.
- heartbeat_at bumped by appendEvents() on each log flush (store.ts:159-191).
- Crash detection is DERIVED ON READ: a 'running' row with null or >10min-old heartbeat reads as
  'crashed' (deriveStatus(), store.ts:37-46; RUN_HEARTBEAT_STALE_MS = 600000).
- Stage `attempts` count (retries) is recorded; per-attempt detail is not.

HARD CEILINGS (these bound any redesign):
- NO mid-stage progress signal. `beat()` (guard.ts:100-104) only resets the stall watchdog; it
  emits no event. A 10-minute stage is an opaque black box from start to end. "Fetched 50 of 120"
  is NOT available without new instrumentation.
- Failure `elapsedMs` is measured from RUN start, not STAGE start — a per-stage failure duration
  needs a change or a derivation from the stage array.
- `dropsByRule` is keyed by the job's FIRST-failing rule per stage only (buildFunnel(),
  result.ts:33-39). Cross-stage per-job lineage is not reconstructable from result_json; the
  `checkpoints` table does carry a `dropped[]` payload, so lineage is theoretically reachable
  from a different table.
- runStore failures degrade to a no-op store (runId -1) — observability can silently vanish while
  the run succeeds. Checkpoint writes, by contrast, are fail-loud.
- Known limitation from CLAUDE.md: farm's funnel reports jobsIn: 0 (farm is additive). Cosmetic
  but it WILL show up in any funnel UI as a bogus row.

## Recon digest D — daemon / intent lifecycle

Path: click → POST /api/profiles/:name/run-intents → `RunIntentStore.request()` inserts a
`pending` row (dedup: returns existing pending with `deduped:true`). Partial unique index
`idx_run_intents_one_pending` guarantees at most ONE pending intent
(migrations.ts:111-121). Pre-insert guard: if newest run is `running`, return 409
`run_in_progress` with runId (intents/routes.ts:48-65).

Daemon (`src/ops/daemon/daemon.ts`): TICK_MS = 30s, immediate first tick on start. Per tick it
reads pending intents across all profile DBs oldest-first, drops ones >10min old, then
`claimIntent()` flips pending→claimed atomically; on success `spawnRun({slot:'intent'})` and
AWAITS child exit (this is the one-Chrome invariant — sequential, not a queue).
`attachIntentRun()` then back-fills `claimed_run_id` by finding the newest run with
startedAt >= claim time (daemon.ts:208-229 in cli/wire/daemon.ts).

Latency: 0–30s, ~15s average, plus pipeline startup. If a prior run is in flight the intent
waits for it to finish AND for the next tick.

Observable transitions for the UI: pending → claimed → (runs row appears, `running`) →
passed/failed/crashed. TWO tables must be polled and correlated via `claimedRunId`.

Failure modes and how the UI can currently detect them:
- Daemon stopped → intent sits `pending`, reads as `expired` after 10 min (derived, never
  written). UI shows "Daemon isn't running". So a stopped daemon costs a 10-MINUTE WAIT before
  the user is told anything. This is the single worst latency in the current experience.
- Child exits non-zero → logged as `child-exit` in daemon logs only; the board never sees it.
  If the crash preceded the first heartbeat the run row may sit `running` until the 10-min
  staleness rule flips it to `crashed` on read.
- Intent cancelled between scan and claim → daemon logs `intent-vanished`, no run created.
- Cancellation works ONLY pre-claim. Once claimed there is NO abort path from the board.
  An in-flight run cannot be stopped from the UI at all.
- `claimed_run_id` has a race window: claimed intent with no run row yet is a legitimate
  transient state the UI must not misread as failure.

- Grid — rows = stages, columns = runs, colour-coded cells — is Airflow's primary run view and
  the single densest way to show both "what failed" and "is this a trend".
- Error summary/log preview shown before the full log; full log on click (Airflow Task
  Instance view).
- Liveness signal on long jobs: elapsed clock + streaming with BACKSCROLL, so the user can
  tell "stalled" from "catching up" (GH Actions live-tail).
- Chronological lifecycle timeline (start/complete/error/retry), filterable — not a raw dump
  (freeCodeCamp).
- Hover shows the error summary; click opens the log. Hover-first, click-second.

DIFFERENTIATORS: recent-runs bar chart for trend; per-stage duration encoded visually to spot
the slow stage; exemplar links (summary element → the exact log lines behind it).

INFERENCE, not sourced (flag as such in the spec):
- Distinguishing "ran fine, found nothing" from "broke silently" with a DISTINCT visual state
  is not addressed by any source — it is a local-tool responsibility and, for a scraper, the
  single most important distinction. Zero JDs is normal; zero JDs because login expired is not.
- Per-stage stall detection relative to that stage's own historical baseline (a uniform stall
  threshold is wrong when stage durations differ by an order of magnitude).
- Funnel as "in → out" per stage read left-to-right.

ANTI-PATTERNS for a single-user local tool: metrics theater (CPU/memory that never explains a
failure); auth/RBAC/audit bloat; over-dashboarding with KPI cards that crowd out single-run
debugging; uniform stall timeouts across unlike stages; log-first instead of summary-first;
rendering "zero results" identically to "connection error".

### The four open usability concerns — RESOLVED by product-ux (do not re-open)

- (a) calm-empty vs urgent-broken → **urgency is encoded as VISUAL WEIGHT, not hue.** Calm rows are
  the lightest thing on the page (no border, no tint, no badge); urgent rows are the only rows with
  a left border + tint + filled icon. Survives greyscale and peripheral vision. Redundant second
  channel: calm **positively asserts health in words** ("Ran clean · 10/10 stages · 214 scraped,
  0 passed filter"), so the language carries the distinction alone if the unsourced visual
  hypothesis fails. Contrast rule: calm = *fewer elements*, never *fainter text*.
- (b) live vs history on one route → **zero live chrome when idle** (no placeholder). A one-row
  ~64px strip between header and panes when live. The live run **never steals the detail pane** —
  it offers `[View]`. Live and history are the same list.
- (c) 10-stage rail glanceable → 10 segments chunked **3/3/4** (acquire/understand/decide), exactly
  ONE visually distinct segment at a time, and a **mandatory text partner** ("stage 5 of 10 —
  structure"). Test applied: delete the rail and the sentence still works — it is an accelerator,
  not a widget. R14 upgrade = swap `flex-1` for `flex-grow:<elapsedMs>`, no markup change.
- (d) funnel shape → **table with an inline retention bar**, not a waterfall, not a chart. 10 fixed
  rows, one user, no comparison need; no charting dependency is pre-approved. `farm` renders `—`
  with an "additive" explanation and an outward bar, never `0`, and is excluded from retention math.

### Design decisions carried forward

- Outcome vocabulary is **7 treatments**: produced / ran-clean-empty / **degraded** / failed /
  crashed / running / **unrecorded**. `degraded` and `unrecorded` are derivations (R6 class iv
  "zero-yield-but-*healthy*" implies an unhealthy sibling; R10 implies unrecorded), not additions.
- **"Calm is earned, not defaulted"** — a zero-yield run renders calm only if a health gate passes:
  10/10 stages && no failure && no open breaker && soft-error rate below threshold.
- Detail panel order is **fixed across all outcomes**: outcome header → diagnosis → rail → funnel →
  evidence. Content Priority #6 is satisfied by lifting the *evidence summary* into the diagnosis
  panel while the *full log* stays last.
- Diagnosis panels: exactly ONE primary action each (Hick's). Class ii's button is disabled with a
  countdown. Class iv has NO button by design. Fallback invents no diagnosis.
- S7 telemetry-missing shows ONLY its panel — no rail, no funnel, no events. The absence is the design.
- Efficiency: **persistent last-run line in the sidebar block** makes JTBD-1 a zero-click answer from
  any route (default landing is `triage`, not `runs`). Killed: detail Refresh button, always-visible
  event level filter, "0 high matches" badge, idle live placeholder, cancel confirmation.

### OPEN ITEMS product-ui must not lose

1. **R9 is load-bearing for R2 but is only a Should.** The health gate that earns the calm state
   leans on soft-error aggregation. If R9 slips, the gate degrades to `10/10 stages && no failure &&
   no open breaker`, and a run that limped through with 40 per-URL failures can still render calm.
   **Recommendation: promote R9, or soften the calm copy to match what the gate can prove.**
2. **Two of R6's five classes live on a different surface.** Class (iii) daemon-not-running never
   produces a run row, so it cannot appear in run detail — it surfaces in the sidebar block and the
   live strip. An implementer reading R6 literally will trip over this seam.
3. **UX-added, not in R1–R8:** the `[View them →]` link from a run's yield to the jobs it produced.
   No such link exists today (recon confirmed) and the Tech Story's completion moment is "I go read
   them". Needs backend confirmation that jobs are attributable to a run. Cut it if they are not —
   the rest of the design does not depend on it.
4. **Assumption for product-ui to verify per stage:** which of the 10 stages have a meaningful
   jobsIn/jobsOut at all. Design rule is `n/a + one-word reason`, never `0`, for any that do not.
5. The mockup substitutes a system font stack for Geist/Nunito (offline constraint), and uses
   hand-drawn lucide-style inline SVG rather than the real lucide icon set.
