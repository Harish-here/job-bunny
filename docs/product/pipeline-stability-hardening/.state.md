Preceding `run_events`: `net::ERR_NAME_NOT_RESOLVED`, `goto(linkedin.com/jobs/search) timed out`,

**ROOT CAUSE — the laptop lid, NOT a merge.** Merge hypothesis ruled out by timing: PR #99

Mechanism (verified vs `pmset -g log`):
1. `Sleep: Entering Sleep due to 'Clamshell Sleep'` 2026-08-12 00:24:11 local; lid closed all

2. Host surfaced for ~2s `DarkWake from Deep Idle [CDNP]` ticks roughly every 15 min.
3. Schedule grace window 90 min (`graceMinutes` default, `src/core/config/schema.ts:14`;
   `harish` does not override). Slots 09:00, 11:30, 14:00, 16:30, 19:00. Missed slot stays
   "owed" 90 min.
4. `src/core/schedule/owed.ts:51` — `if (now < slotAt || now > graceEndAt) continue;` — pure
   wall-clock. Each DarkWake, the 30s tick (`TICK_MS = 30_000`, `src/ops/daemon/daemon.ts:39`)
   saw a still-owed slot and spawned. Spawn times (09:19:10, 11:39:56, 14:10:26, 16:40:10,
   19:43:10 local) align with logged DarkWake ticks nearly to the second.
5. Chrome launched into a host whose network had not reassociated -> DNS failures, nav timeouts.
6. Host slept again mid-run. Stall watchdog `src/pipeline/runner/guard.ts:90-94` is

   `DEFAULT_STALL_MS = 360_000` (`src/cli/commands/run.ts:55`, hardcoded, not configurable).

**Architectural finding:** the pipeline uses wall-clock time as a proxy for progress. On a
host that suspends, the two decouple. Every deadline inherits this — `guard.ts:90`,
`src/pipeline/runner/run.ts:43` `AbortSignal.timeout(opts.runCapMs)`, all per-stage
`timeoutMs`. Consequence: **a run started on a suspended host cannot succeed.**
Deterministic, not flaky.

**Ruled out (do not spend effort):** Chrome process leak (none — all 54 processes accounted

frame in any `failure_json`; `reconcile` succeeded cleanly every time).

### The three defects to spec

**D1 — The daemon starts runs the host cannot finish.**
- No preflight connectivity check anywhere in the run path (grepped `navigator.onLine`, `dns`,
  `lookup`, `preflight`, `healthCheck`). Only probe is CDP reachability at
  `src/adapters/browser/cdp-chrome/provider.ts:210-212`, a 2000ms fetch to
  `http://127.0.0.1:9222/json/version` — localhost only, and AFTER the daemon already spawned.
- `src/pipeline/stages/farm.ts:71` sets `retries: 0` -> stall abort is fatal.
- `--resume` is opt-in (`src/cli/commands/run.ts:236`); a failed scheduled run never auto-resumes.
- Daemon already persists `lastTickAt` in its pidfile every tick
  (`src/ops/daemon/daemon.ts:271-276`). `now - lastTickAt` is a **free suspend detector** —
  nothing else stalls a 30s interval for minutes.

**D2 — A schema migration silently disables the running daemon. This one IS merge-caused.**
- `~/.jobbunny/logs/daemon.log` lines 104-228, 2026-08-11T03:59:00.119Z -> 06:00:22.600Z,
  **75 occurrences**: `SqliteRunStore: failed to open .../jobbunny.db: Error: jobbunny.db
  schema v7 is newer than this build supports (v6)`
- Cause: `jobbunny` bin symlinked to the working checkout, so `jobbunny run` children migrated
  the DB to v7 while the long-lived daemon still held v6 code in memory. Logged 75x over two
  hours, kept ticking uselessly. Recovered only via manual restart (new PID 77885, 06:26:22Z).
- `LATEST_SCHEMA_VERSION = 7` at `src/adapters/db/sqlite/store/migrations.ts:16` (v6->v7 by
  PR #99, which added `run_progress`).
- **Will recur on every future schema bump.** Failure direction is safe (refuses rather than
  corrupts) but there is no detection, no self-heal, no visible alert.

**D3 — Failure notification has no storm guard; no status expresses "not attempted".**
- `src/cli/commands/run.ts:308-312` sends the digest unconditionally, once per run, both
  outcomes. No dedup, no rate limit. Six failures = six identical Telegram pages overnight.
- `src/ports/run_store.ts:7` — `export type RunStatus = 'running' | 'passed' | 'failed' | 'crashed';`
  No value meaning "deferred / not attempted". Actual DB values: `passed` 14, `failed` 9,
  `crashed` 1, `running` 1.

### Decisions already made (DO NOT REOPEN)

1. **Scope = all three defects (D1 + D2 + D3).** User chose this explicitly over narrower options.
2. **Do NOT make the stall watchdog suspend-aware; do not touch `src/pipeline/runner/`.**
   Deliberately rejected: a forgiving watchdog would not have rescued those runs (network down,
   CDP socket dead) — it would only convert a 16-min failure into a run that hangs across sleep
   cycles until the run cap. Highest blast radius in the repo for negative benefit.
3. **The fix belongs at the daemon: do not start runs the host cannot finish.** Two
   complementary gates, both cheap: (a) suspend detection from the `now - lastTickAt` gap,
   (b) a bounded reachability probe before spawn. Complementary because DNS may answer during a
   DarkWake (TCPKeepAlive active) even though the host is about to sleep again.
4. **Safety property that makes the gate acceptable:** a gated slot stays owed inside its
   90-min grace window, so the next 30s tick retries. A transient probe failure costs 30
   seconds, not a slot. Preserve this in the acceptance criteria.
5. **Host-side mitigation is NOT part of this feature** but is noted as operator guidance:
   Amphetamine holds `PreventUserIdleSystemSleep` (70+ hrs, verified via `pmset -g assertions`)
   but that assertion does not override clamshell sleep. Lid closed = asleep; operator either
   keeps the lid open during slots or uses `pmset repeat wake`.

### Repo constraints the spec must respect

- Stability principle: changes touching `pipeline/`, `runner/`, `adapters/`, `ports/` reviewed
  for blast radius and failure modes, never shipped on unit tests alone.
- Layer boundaries mechanically enforced by `npm run boundaries`. `core/` pure; `ports/` imports
  only `core`; only `cli/wire/compose.ts` instantiates adapters.
- Two-pair rule: module = folder with `index.ts`; >2 impl files gets split.
- File-size caps: 400 impl / 800 test.
- Runtime deps capped at three (`@notionhq/client`, `playwright`, `zod`) + `dotenv`. A
  reachability probe must use `node:` builtins, not a new dependency.
- `jobs` and the runs tables stay pipeline/runner-only — structural split (`ports/board.ts`).
- Gate: `npm run check`, 3-OS matrix. `main` protected.
- **Cross-platform** (macOS/Windows/Linux). Suspend/resume is not darwin-only; Windows sleep and
  Linux suspend produce the same wall-clock gap. Spec must not assume darwin.

Persona: the single operator of a personal job-search tool who relies on unattended scheduled

## AMENDMENT 2 — 2026-08-13, metric correction (coordinator caught a permanently-red metric)

**The freshness metric I added in Amendment 1 was broken as written.** "No gap greater than ~12
hours between successful runs" — against the configured slots (`09:00, 11:30, 14:00, 16:30, 19:00`)
a perfectly HEALTHY day ends at 19:00 and resumes 09:00 = **14h gap every single night**, already
over threshold. The bad case it targeted (11:30 success, lid closed, no catch-up, next success
09:00) = **21.5h**. A 12h threshold flags both identically, so the metric would have been red
forever and told the operator nothing.

**Chose option 2 of the two offered — unserved-window tail — over raising the threshold.**
New text: "No more than ~3 hours of the schedule window elapses after the last successful run of
that day", measured on days the host was awake at or after the window's end.
Arithmetic recorded in the spec: healthy day tail = 0 (19:00 success, window ends 19:00);
partial-sleep-without-catch-up = 7.5h (11:30 success vs 19:00 window end); partial-sleep WITH
catch-up firing 20:12 = 0 (lands after window end). Adjacent slots are ≤2.5h apart by construction,
so one missed trailing slot stays under threshold and only a genuine unserved stretch trips it.

**Why option 2 over option 1 (raise to ~16-18h):** option 1 works but requires the threshold to
thread between two overnight gaps (14 vs 21.5) and must be RE-DERIVED for any change to the slot
list — a per-profile retune that nothing in the system would remind anyone to do. The tail
formulation removes the overnight gap from the arithmetic entirely, so it is threshold-stable
across any schedule. Cost, stated in the spec: less intuitive to read at a glance than "hours since
last run". Accepted that trade — a metric that is red every night by construction is worse than one
that needs a sentence of explanation.

**Audit of the other metrics against "would a healthy system pass this?" — 1 more defect found:**
- **"No calendar day with zero successful runs where the host was awake..."** — DEFECTIVE, exactly
  as the coordinator predicted. A host awake but OFFLINE all day is a day where the gate correctly
  declines every slot and zero runs is the RIGHT outcome; the metric would have scored the feature
  as failing for working. Fixed by adding "**and had working connectivity**", with a note that both
  qualifiers are load-bearing.
- **Suspend-signature metric** — softened. A network dying mid-run on a fully awake host produces
  the identical signature (`stalled: no beat()` after `ERR_NAME_NOT_RESOLVED`), and no PRE-spawn
  gate can prevent that. Now scoped to runs where the daemon's tick history shows a suspend gap
  shortly before the run started, so the metric measures what this feature actually controls.
- **"At most 2 notifications per 24h for any single ongoing failure"** — PASSES unchanged. Dedup is
  per-signature, so two distinct concurrent failures legitimately yield up to 4 messages without
  violating it; success digests are excluded by R20 and not counted here.
- **"100% of deferred entries carry non-empty reason text"** — PASSES unchanged. No healthy-system
  false positive; a blank reason is unambiguously a defect.
- **"Time from schema bump to operator awareness"** and the **qualitative** metric — PASS unchanged.

Net: 2 of 6 metrics were defective (the new freshness one and the zero-runs one), 1 needed
tightening, 3 clean. Nothing else in the spec reopened.
